Equipment reliability & LNG planning

From machine readings
to a useful next step.

I built a local data science workflow to identify machines needing a maintenance review and forecast monthly LNG exports from a terminal.

Runs on a laptop with Python and SQL. Equipment results use Microsoft's simulated machine data; terminal forecasts use public DOE export records. These are separate demonstrations, not connected plant measurements.

How I built it

One reproducible workflow. No cloud account.

01 / Ingest

Download five machine tables and a DOE workbook. Keep the originals, source URLs, and file checksums.

02 / Prepare

Validate records, quarantine bad rows, and build time-aware joins in DuckDB. Save clean tables and features as Parquet.

03 / Model

Compare a rule, MLP, and XGBoost. Choose settings on earlier months; test on later months and unseen machines.

04 / Score & review

Reload the saved model, replay incoming history, suppress stale inputs, and produce a bounded review queue.

$telemetry_rows sensor records → $feature_rows decision rows · $raw_rows LNG transaction records · $quarantined record(s) quarantined

See what happens during preparation and modeling
  1. Validate schemas, machine IDs, positive sensor values, timestamps and duplicate keys. Store rejected rows separately with a reason.
  2. Join hourly telemetry to error counts and the last component replacement known before each decision. Calculate 24-hour sensor averages and variability, equipment age, and time since maintenance.
  3. At six-hour intervals, label whether any component fails in the next 24 hours. Exclude incomplete future observation windows and failures occurring at the decision instant. Future failures are labels only.
  4. Fit on January–August 2015, validate on September–October, and test on November–December. Purge overlapping 24-hour label windows. Hold out every fifth machine from all fitting and tuning.
  5. Select the highest validation incident recall within an illustrative budget of two false reviews per 100 machine-days. Limit review requests to one per machine per 24 hours. Save models, thresholds, versions, metrics and input hashes.

SQL transformations are in sql/features.sql. Python handles validation and modeling. The source timestamps have no documented timezone or arrival delay; the demonstration assumes values are available at their recorded time and excludes current-time sensor values from features.

“Known machines” are evaluated on later months; “unseen machines” were excluded from training and validation entirely. The selected model stays fixed across both groups. A review is false if no recorded failure follows within 24 hours. Exposure is six hours per eligible scoring row, expressed in machine-days.

Median lead time excludes missed incidents; the failure counts show their denominator. The alert budget is a proposed portfolio constraint, not an agreed plant requirement. Model scores are not calibrated failure probabilities. These datasets are small, synthetic, and lack repair duration, intervention outcomes, and maintenance costs; no savings or downtime reduction is claimed.

What is monitored, and what happens when data is missing?

The replay records scored and suppressed machines, review counts, and feature means moving more than three training standard deviations. This distribution check is a diagnostic, not a validated drift alarm. Missing hours or a stale latest observation suppress a machine's score instead of filling in invented readings.

The local model registry records model checksums, feature names, settings, library versions and source hashes. Replay verifies the model checksum before loading. Tests check that replay scores match offline scoring and future input changes cannot alter past features.

Review the backtest and reporting assumptions$export_table

The baseline carries the latest available daily rate into the forecast month. Learned models predict its change from calendar seasonality and growth known at the cutoff. A 12-month validation period precedes the final 24 test months; model settings are then frozen. Training targets also stop at the availability cutoff.

The three-month lag is a conservative fixed assumption, not a reconstruction of each historical release. The pinned workbook includes revisions. Vessel allocations are preserved and summed; a transaction row is not assumed to equal a whole cargo. Re-exports and ISO-container shipments are excluded.

A plant production forecast would require train output, availability, feed-gas constraints, maintenance, and operating mode. No simulated machine data is joined to these real terminal records.

How this maps to the role

A local implementation of the data science lifecycle.

Data engineering

Python ingestion, source lineage, quality checks, SQL joins and Parquet tables.

Predictive modeling

Future-event labels, simple baselines, validation, held-out equipment and operational metrics.

Maintenance & delivery

Saved model artifacts, repeatable scoring, monitoring, automated tests and CI.

Senior-level decisions

A data contract, model card, pilot acceptance gates and a runbook another analyst can follow.

Where Azure and Databricks would fit later

The local runner serves the scheduling role; raw folders provide the landing layer; DuckDB and Parquet provide queryable storage and transformations. In a cloud implementation, Data Factory could orchestrate ingestion, Data Lake hold the files, and Databricks run preparation and model jobs. These are architectural counterparts, not claims that this project runs Azure or distributed Spark.

Begin a plant pilot with one train and an operations owner. Approve event definitions, acceptable lead time and review capacity; validate on later periods and other trains; then run alongside current processes. Keep approved alerts and planning methods as fallback. Read the pilot plan.
